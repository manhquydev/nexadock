### 5.2. Deep-Dive on Error Scenario #7 (Corrupted Data) — Honest UX Findings

While backend data integrity passed every fail-closed invariant (`DEFECT-08c`: `0`-byte or malformed `profiles.json` is never silently reset; tampered backup files fail SHA-256 verification before any profile directory is promoted), our user-perspective audit uncovered three open UX requests filed in [`integration-requests.md`](./integration-requests.md):

1. **Pre-existing `profiles.json` corruption before Native Tauri launch (`IR-QA-UX-01`, `P1`):**
   - `apps/desktop/src-tauri/src/main.rs:9` calls `AppState::initialize().expect(...)`, which validates `profiles.json` before opening the Tauri window. In release builds (`windows_subsystem = "windows"`), `dim-desktop.exe` exits immediately with no window if `profiles.json` was damaged prior to launch (whereas Signed-Host Bridge `ui-server.mjs` opens the UI and displays an error banner).
2. **`JSON_ERROR` refresh guidance & Tauri `get_status` error flattening (`IR-QA-UX-02`, `P1`):**
   - `corrupt_profiles_json_error` (`store.rs:543`) returns `DimError::Json` -> `JSON_ERROR`, whose UI copy tells the user *"Hãy thử làm mới lại"* / *"Please try refreshing"* instead of directing them to **Troubleshoot** or **Backups** (`SCHEMA_ERROR`). In Native Tauri, `get_status` returns `Err(String)` and `app.js:178` maps it to `HOST_EXEC_FAILED` (*"Could not connect to the app"*).
3. **Tampered backup restore displays `BACKUP_ERROR` copy (`IR-QA-UX-04`, `P2`):**
   - `restore_backup_as_new_profile` delegates integrity checking to `verify_backup()`, which returns `DimError::BackupError` (`BACKUP_ERROR`) on SHA-256 mismatch or missing files. Consequently, clicking **Restore** on a corrupted backup displays *"Cannot back up while Zalo is open or the folder is busy"* instead of *"Cannot restore because this backup failed integrity verification"*, and malformed `backup.json` folders are silently skipped by `list_backups`.
